## Where this came from

Continuing from `handover-flow-hooks-and-timeout-consolidation.md`'s open item: `flow_start`/`flow_next`'s single main-run lock (`runs/active.json`) collides across *different* sessions sharing the same project, not just within one session — confirmed via live testing earlier this session (two live e2e tests stepping on each other's lock). The fix design: key the lock per session (`runs/active-{session_id}.json`), using `CLAUDE_CODE_SESSION_ID` env var for Claude (confirmed reaches the MCP server subprocess — verified live) and the `tools/call` request's `_meta.threadId` for Codex (confirmed via a live `codex exec` test — Codex exposes **no** session/thread env var to spawned MCP servers, confirmed both via the closed-as-not-planned GitHub issue openai/codex#19937 and a live test, but **does** carry `threadId`/`x-codex-turn-metadata.session_id` in every `tools/call`'s `_meta`).

Threading Codex's `_meta` into the harness required first reading it out of `mcp-server/protocol.py`'s dispatch loop — which then triggered a full-file SOLID re-review of that whole file (pre-write gate re-reviews the *entire* file on any touch, not just the diff), which snowballed into fully decomposing `protocol.py` (renamed `mcp_transport.py`) into ~35 small SOLID-compliant files. **That decomposition is unfinished and not wired into any live server yet** — see below.
