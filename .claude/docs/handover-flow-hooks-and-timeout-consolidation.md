## What shipped today

### 1. Flow engine error handling (`flow_next`/`flow_start`)

- `RunCompletionChecker` now populates `FlowNextResult.error` with a concrete message on `failed`/`timed_out` — names the step, attempts used, last rejection reason, the run's `events.jsonl` log path, and an explicit "stop, do not retry, report to the user" instruction. Previously these statuses carried zero detail.
- `attempts_remaining` removed entirely from `StepResult`/`FlowResultRenderer`/the JSON renderer — per-step rejection messages no longer tell the LLM "you have N attempts left" (was inviting mechanical retries instead of diagnosis). Terminal exhaustion still reports attempts *used* (backward-looking), just not remaining (forward-looking).
- Uncaught `InterpolationError` crash fixed — `flow_starter.py`/`flow_stepper.py` now wrap the previously-unguarded `run_ready()` call site (via a new `FlowStepper._guard_interpolation` helper, added specifically to avoid a 3-way duplicate of the same try/except the health-check gate flagged).
- `pipeline/server.py`'s `flow_next` tool description rewritten to match — no longer promises "how many attempts remain."
- Verified: full 250-test flow_engine suite + the live e2e test (`test_flow_e2e_live.py`) green.

### 2. Codex e2e stale-plugin hang — root cause + fix

- Root cause: a stale, globally-installed codex plugin (`~/.codex/plugins/cache/local-marketplace/solid-coder/1.5.1/`, disconnected from this dev repo, same category of issue as [[project_stale_plugin_install]] but worse) fires its own year-old `pre_write_gate.py` independently whenever `codex exec --dangerously-bypass-hook-trust` runs — which itself spawns *another* nested `codex exec`, causing a real runaway (orphaned processes kept respawning children after the parent was killed).
- **First attempted fix, reverted**: `--ignore-user-config` on the codex command. Did stop the runaway, but broke the health check outright — `--profile` layers `$CODEX_HOME/<name>.config.toml` on top of the base config, and `--ignore-user-config` skips that base entirely, so the profile's own `[mcp_servers.*]` never loaded either (`LLM did not call submit_batch_findings`). **Do not re-add this flag.**
- **Actual fix**: `tests/harness/integration_tests/test_codex.py` now writes a project-scoped `<repo_root>/.codex/config.toml` in `setUpClass` (removed in `tearDownClass`) registering this checkout as a local codex plugin marketplace (`[marketplaces.solid-coder-dev-local] source_type = "local"`, `[plugins."solid-coder@solid-coder-dev-local"] enabled = true`). Project-scoped config wins over global on key collisions, so codex uses the dev-repo plugin instead of the stale snapshot.
- Verified live, twice, via `python3 -m pytest tests/harness/integration_tests/test_codex.py -v -k test_health_flow` (run directly — **not** via `unittest discover`, see below): no hang, no recursive spawn, real `submit_batch_findings` calls succeeding across DRY/ISP/LSP/OCP fixtures.
- **Separate landmine found and documented, not fixed**: `python3 -m unittest discover -s tests` from repo root silently sweeps up `tests/harness/integration_tests/test_{codex,sonnet,opus,haiku,llm}.py` — five live, multi-hundred-real-API-call integration suites, despite each one's own docstring saying "run explicitly via pytest." This is what caused the original 29-minute silent hang this session started with. Not fixed at the harness level (no `__test__ = False`-style discovery guard) — flag before ever running a repo-root-wide test sweep here.

### 3. Stop hook: `flow_transition_gate` + attempt-exhaustion safety valve

New files (all under `mcp-server/hooks/` unless noted):
- `flow_transition_evaluating.py` — `FlowTransitionGate.evaluate(run_id=None) -> dict`. Checks `flow_status()`; if `in_progress` with a pending step, delegates to `PendingStepFailureRecorder.record(run_id, step_id)` (records the block as a failed attempt against that step — the *same* accounting a rejected submission uses) and returns that recorder's terminal error message if the step's own `max_attempts` just got exhausted, otherwise a generic "call flow_next" message. Also exports `build_default_flow_transition_gate(base_dir_resolver=None)`, the production wiring factory.
- `pending_step_failure_recording.py` / `pending_step_failure_recorder.py` — protocol + impl, split out of `flow_transition_evaluating.py` after the health-check gate flagged it as doing too much (SRP). Locates the run, loads its flow_def, calls `AttemptFailureHandler.handle(...)`.
- `flow_transition_gate.py` — the actual Stop-hook script. `main(gate=None, responder=None)`.
- **The safety valve** (added mid-session after realizing the original design blocked indefinitely with no escape — exactly the runaway-loop risk this whole session was fighting elsewhere): each block increments the pending step's `attempts_used` via the existing event-sourced path. First N-1 attempts (default `max_attempts=3`): generic block, "call flow_next." On exhaustion: `RunCompletionChecker` marks the run `failed` (reusing item 1's concrete-message work above) and *that* message becomes the block reason — the run's own status then reads `failed`, so the *next* Stop-hook evaluation naturally returns `allow: True` (no special-casing needed; falls out of the existing `status != "in_progress"` check).
- Verified deterministically via `tests/harness/flow_engine/checkers/...` — no, actually via `mcp-server/hooks/tests/test_flow_transition_gate_integration.py`: real on-disk runs (real `FlowRunOrchestratorFactory`, no stubs), including `test_allows_after_three_blocked_stop_attempts_exhaust_the_pending_step` (calls `main()` four times directly, asserts block→block→block-with-exhaustion-message→allow).
- Verified live twice via `tests/harness/flow_engine/test_flow_transition_gate_e2e_live.py` (new; uses `--plugin-dir` so this dev repo's hook loads, not the stale global install — see item 2's pattern; reuses/extends `test_flow_e2e_live.py`'s `_run_claude_non_bare`/`_spawned_by_header` rather than duplicating them, after an earlier draft of this file wrongly reinvented its own near-duplicate helper and dropped the `spawned-by:` traceability tag). Both live runs confirmed the hook genuinely fires and records `step_attempt_failed` in a real session — but neither run reached a full 3-attempt exhaustion sequence live (the agent's own session ended after 1-2 blocks each time; LLM non-determinism in reacting to a block, not a hook bug — the exhaustion path itself is already proven deterministically by the integration test above).
- Wired into `hooks/hooks.json` as a new `Stop` array entry.

### 4. Hook response architecture: typed models + unified responder pattern

Prompted by repeated pushback this session against ad-hoc `.get()`-on-raw-dicts and inconsistent block/allow mechanisms across hook scripts:
- `mcp-server/hook_utils.py` gained `parse_json_safely()`, `StopHookEvent` (typed dataclass: `stop_hook_active, session_id, transcript_path, cwd, last_assistant_message`), `parse_stop_hook_event()` — `parse_hook_event()` (existing, PreToolUse) now reuses `parse_json_safely` too, closing a 3-way duplicate the gate flagged.
- **Verified against real Claude Code docs** (not assumed from existing repo code, which itself might have been guessing): `Stop`/`SubagentStop` payload schema is `session_id, prompt_id, transcript_path, cwd, permission_mode, hook_event_name, effort, last_assistant_message` + `stop_hook_active` (Stop-only) or `agent_id`/`agent_type` (SubagentStop-only). No parent-session or task-correlation field exists in either — confirms the plan's transcript-scanning design for the future SubagentStop hook is the only viable mechanism, not a shortcut we missed.
- **Session-id correlation idea ruled out** for disambiguating a flow-driving subagent from its parent: Claude Code subagents run *within the same session* (context isolation, not process separation) — no distinct `session_id` per subagent. Codex doesn't even expose a session-id env var to MCP servers yet (open, unimplemented feature request). Independently reconfirms what an earlier session already concluded via a different angle ("no protocol-level signal to distinguish caller context").
- **Block mechanism switched** from `on_agent_stop.py`'s exit(2)+stderr convention to the *documented-preferred* form: flat `{"decision": "block", "reason": ...}` JSON on stdout, exit 0 (confirmed via docs — `Stop`'s JSON is flat, unlike `PreToolUse`'s nested `hookSpecificOutput`). This is now unified with the existing `HookResponding` abstraction (`hook_responding.py`/`HookResponder`/`HookGate`) rather than duplicating stdout-writing logic ad hoc:
  - `simple_hook_responding.py` — new, narrower `SimpleHookResponding` protocol (`allow()`/`block()` only — no `allow_with_update()`, which has no meaning for Stop/SubagentStop and would've been an LSP violation to fake).
  - `stop_hook_responder.py` — `StopHookResponder(SimpleHookResponding)`, reuses the *same* `StdoutWriter.write_payload()` dump mechanism `HookResponder` (PreToolUse) already uses, just with the flat wire shape instead of the nested one.
  - `hook_utils.run_stop_hook_gate(raw, evaluate, responder, default_reason)` now takes an injected `responder` and calls `.block()`/`.allow()` — never writes stdout/stderr or calls `sys.exit` itself.
- **Not done, still open**: `GateDecision` (typed `allow: bool, reason: str = ""` dataclass) to replace `FlowTransitionGate.evaluate()`'s raw `{"allow": ..., "reason": ...}` dict return and `run_stop_hook_gate`'s `.get()` calls on it. Was mid-edit when the health-check gate's own subprocess started timing out (infra flakiness, not a code issue — confirmed `hook_utils.py` was never left in a broken state on disk). Pick this up first next session — it's a small, well-scoped edit, already fully designed, just not yet applied.

## Next session: timeout consolidation (fully designed, not yet implemented)

Triggered by chasing why a `hook_utils.py` edit kept getting blocked by a gate-infra timeout — surfaced a real, pre-existing bug independent of anything above:

- **`LlmConfig.timeout` is dead code.** Zero production consumers anywhere in `mcp-server` (confirmed by grep) — only exists in config-parsing tests that check it round-trips. The value actually governing the health-check session (uniformly across all three backends — claude, codex, *and* local, all via the same `LLMExecutor.execute(timeout=...)` wrapper, confirmed by tracing `llm_executor.py` → `hc_llama_runner.py`) is `bare_session_timeout`. Both fields currently sit side by side in `.solid-coder/config.toml` (`bare_session_timeout = 1000`, `timeout = 2000`) and `.solid-coder/config.local.toml` (`600` / `1000`) with different, confusing values — the user has been editing a setting that does nothing.
- **Also confirmed**: both Claude Code and Codex default to killing a hook process after **600 seconds** if the hook's own registration doesn't declare a longer `"timeout"` field — and neither `hooks/hooks.json` nor the codex profile template currently sets one. So today, before any fix, a health check configured for 1000s could already be getting killed by the platform's own 600s ceiling.
- **Agreed plan** (design reviewed with the user, not yet built):
  1. New `mcp-server/health/config/hook_timeout.py` — `HOOK_EXECUTION_TIMEOUT_SECONDS = 1200` (the platform-facing ceiling we declare) and `HOOK_LLM_SESSION_TIMEOUT_SECONDS_DEFAULT = 1000` (the session budget default), single source of truth for both.
  2. `LlmConfig`: delete the dead `timeout` field, rename `bare_session_timeout` → `timeout`, add a `model_validator` that raises `ValueError` (→ `SolidCoderConfigError` via the existing `hc_config_schema.load_config()` catch) if `timeout >= HOOK_EXECUTION_TIMEOUT_SECONDS`. `extra="forbid"` means a stray old `bare_session_timeout` key left in a TOML file fails loudly at load time — no silent drift.
  3. Rename the two production call sites (`hc_runner_factory.py:46`, `hc_checker_factory.py:87`): `llm.bare_session_timeout` → `llm.timeout`.
  4. `CodexProfileManager._PROFILE_TEMPLATE` gains a `timeout = {hook_timeout}` line in `[[hooks.PreToolUse.hooks]]`, sourced from the constant — this one **can** be kept truly in sync automatically, since the profile is generated fresh every time (unlike Claude's static file).
  5. `hooks/hooks.json`'s `pre_write_gate` entry gets a literal `"timeout": 1200` (JSON can't reference a Python constant, so this is the best achievable — paired with:
  6. **New test** that reads `hooks/hooks.json`, parses the `pre_write_gate` entry, and asserts its `"timeout"` literally equals `HOOK_EXECUTION_TIMEOUT_SECONDS` — converts "must be kept in sync manually" into "fails a test immediately if it ever drifts."
  7. Consolidate the two TOML files' duplicate/conflicting lines into one `timeout = 1000` each, with a comment pointing at `hook_timeout.py` and `hooks.json`'s value.
  8. Test updates: rename `bare_session_timeout=` → `timeout=` in `test_runner_strategy_env.py`, `test_hc_codex_runner.py`, `test_validate_swift_frontmatter_fix.py`; extend `test_hc_profile_toml_validity.py` for the new `timeout` line; new test for the `LlmConfig` validator; `test_hc_config_defaults/_overrides/_validation.py` need **no changes** (both old fields defaulted to `300`, so the generic parsing-mechanics tests keep passing unchanged under the renamed field).
- **Investigated and ruled out**: dynamically declaring the hook's timeout via `claude --settings <json>` instead of the static `hooks.json` file (would've been a nicer parallel to codex's fully-dynamic profile generation). Came back fully undocumented/uncertain on every question that mattered (whether `--settings`-declared hooks even execute, how they'd merge with the static file) — not worth building on unverified platform behavior, especially after this exact session's earlier lesson about the same thing (codex plugin marketplace schema). Stick with the static-file-plus-drift-test approach above.
- **Confirmed not a concern**: the "local" backend needed no special-casing in any of the above — it was already correctly wired through the same shared `LLMExecutor`/`hooks.json` mechanisms as claude/codex, by construction, not by lucky accident.
